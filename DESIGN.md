# DESIGN.md — Визуальный контракт Battlefield

> Создано вручную в рамках Battlefield Art Pass. Skill `create-design-md`, изначально указанный
> владельцем как обязательный инструмент для Фазы 1, не установлен в этой сессии (в `.agents/skills/`
> присутствуют только `better-ui`, `image-to-code`, `playwright-cli` — остальные 10 ранее
> установленных skill'ов не пережили сброс окружения, и `create-design-md` в их числе никогда не
> было). Содержимое ниже фиксирует те же решения владельца, которые Фаза 1 требовала записать
> дословно, написанные напрямую. Это — раскрытое отклонение от буквальной инструкции, а не
> подмена результата.

## 1. Природа интерфейса

Battlefield — это художественный магический игровой стол, а не SaaS-интерфейс и не типовой
веб-дашборд. UI обязан выглядеть как физическая часть стола: металл, золото, камень, сапфировые
линзы, гравировка, свечение, объём и врезанные механизмы.

Утверждённые PNG/WebP-файлы и прорисованная геометрия стола — основной источник визуальной
истины. HTML-разметка накладывается поверх готового арта, чтобы дать игровую логику
(клики, состояния, доступность), но не заменяет сам арт.

## 2. Что запрещено

- Deck, Discard, Resonance, End Turn никогда не должны становиться обычными карточками, панелями,
  «pill»-кнопками, кругами, квадратами или плоскими CSS-блоками.
- Готовые декоративные механизмы никогда не заменяются CSS-градиентами, бордерами, тенями,
  простыми SVG-кольцами или псевдоэлементами.
- Поверх существующего художественного языка нельзя надстраивать новую универсальную дизайн-систему.

## 3. Desktop / Mobile

Desktop и mobile могут иметь разную композицию, но обязаны сохранять единую художественную
вселенную. Любая визуальная работа принимается только после проверки реального рендера на
согласованных разрешениях.

## 4. Текущее состояние на момент начала прохода (коммит `d9f4115`)

Проверка исходников на этой ветке показала, что независимо от наличия утверждённых
production-ассетов, все четыре контрола изначально были реализованы полностью через CSS/SVG-примитивы, без
единой ссылки на растровый арт:

- **`EndTurnArtifact.tsx`** — ручной SVG-круг (`<circle>`/`<line>` тики), CSS `radial-gradient`
  «мышца» кнопки, повернутые бордер-квадраты как рунные крепления. Файл не подключал
  `kod-raido-end-turn-master.webp`, хотя этот ассет уже закоммичен в
  `apps/web/public/art/battlefield/controls/`.
- **`DeckPile.tsx` / `DiscardPile.tsx`** — слоистые «карты» нарисованы через `border` +
  `bg-gradient-to-b` + `box-shadow`, счётчик — CSS circle-бейдж, discard-плита — CSS
  `rounded-md` с клип-путями для «трещины» рун.
  Растровых ассетов для этих элементов не существует нигде в репозитории (см. раздел 6).
- **`ResonanceMeter.tsx`** — типовой HUD-блок: `rounded-xl` панель + ряд CSS-кружков-индикаторов
  (`ring-2`), т.е. буквально обычный progress/HUD-виджет, чего требование прямо запрещает.

Это подтвердило claim владельца: утверждённые механизмы были упрощены до кругов, квадратов, рамок
и CSS-контейнеров.

## 5. Почему так вышло

Компоненты были написаны до/без интеграции конечных растровых ассетов — либо ассеты появились в
репозитории позже (см. `kod-raido-end-turn-master.webp`), либо для Deck/Discard/Resonance
подходящих production-ассетов вообще не поставлялось, и авторы закрыли геометрию вручную через
Tailwind-примитивы как временное решение, которое затем осталось финальным.

## 7. End Turn — обязательные правила интеграции

- Использовать **только** `apps/web/public/art/battlefield/controls/kod-raido-end-turn-master.webp`
  как единственный decorative-слой: `pointer-events-none`, `aria-hidden`, `draggable={false}`,
  оригинальные пропорции, без кропа/растяжения.
- Запрещено: рисовать поверх SVG-кольцо, собирать корпус градиентами/бордерами/psevdo-элементами,
  использовать старый lens-only ассет, помещать арт в квадратную/круглую UI-плашку.
- Интерактивность — прозрачная круглая `<button>` поверх внутренней сапфировой линзы (54% от
  диаметра самого арта, пиксельно измерено). Внешний золотой корпус не кликабелен.
- Ровно один персистентный `<button data-tutorial-target="end-turn">`, сохранены `onClick`,
  disabled-логика, pending-состояние, keyboard-активация, `focus-visible`, ровно один вызов
  `onEndTurn` за клик.
- Состояния: Ready / Hover / Pressed / Pending / Disabled — без новых геометрических оверлеев,
  только тонировка/свечение/масштаб самой линзы; `prefers-reduced-motion` и Low Data Mode обязаны
  полностью гасить transform/pulse.
- Desktop-механизм сидит на нарисованной перспективе стола (см. раздел 8), не фронтально.
- Текст (`ЗАВЕРШИТЬ` / `ХОД` / `ОБРАБОТКА…`) — Cormorant SC Bold, светлая слоновая кость с тёплым
  золотым оттенком (`#f3e6c4`), усиленная тёмная тень, ~25% крупнее исходного размера (владелец
  подтвердил: исходный размер терялся внутри яркой линзы).

## 8. End Turn — перспективная посадка (визуально подтверждена владельцем)

Владелец подтвердил на 1366×650, 1600×720 и 1920×1080: механизм правильно лежит в плоскости
стола и совпадает с нарисованным housing. **Базовые параметры перспективы зафиксированы и больше
не меняются** без отдельного пиксельного перезамера:
`perspective(1000px) rotateX(19deg) scaleY(0.83)`, центр (45.41%, 71.57%) от `.endTurnSlot`,
ширина механизма 111.65% от ширины `.endTurnSlot`. Реализовано в `EndTurnArtifact.tsx` как единая
transform-цепочка, применённая идентично и к decorative `<img>`, и к прозрачному hitbox
`<button>` — поверх неё уже накладывается интерактивный `scale(var(--et-scale))` (hover/press) и,
только на самом button (не на внешнем корпусе), press-only микро-сдвиг
`translateY(var(--et-press-ty))` — база и интерактив разведены по разным частям цепочки, а не
заменяют друг друга.

Два found-and-fixed бага по пути, оба стоит знать при следующей правке этого файла:
- **`--arena-w` нельзя переиспользовать в дочерних кастом-свойствах.** `%`, вложенный в одно
  CSS custom property (`min(100%, ...)`), пересчитывается относительно того элемента, который
  в итоге читает его через `var()`, а не относительно того, где custom property объявлено — на
  глубине этого компонента `100%` внутри `--arena-w` резолвился в размер бокса самого
  `.endTurnSlot`, а не сцены. Все размеры/позиции теперь выражены как обычные проценты от
  `.endTurnSlot` (уже синхронизирован со сценой на каждом viewport), без обращения к `--arena-w`.
- **Tailwind JIT не видит классы, собранные через `${переменная}`**, даже если сама переменная —
  module-level константа, а не React state: он сканирует буквальный текст исходника, не
  выполняет JS. Transform-строки записаны буквально
  (`IMG_TRANSFORM_CLASS`/`BUTTON_TRANSFORM_CLASS`/`POSTURE_TRANSFORM_REDUCED_MOTION_CLASS`), а не
  собраны шаблонной строкой. Отдельно всплыл `img { max-width: 100% }` из Tailwind preflight — он
  молча обрезал механизм обратно до 100% ширины `.endTurnSlot`, хотя decorative-арт должен быть
  шире (~112%) своей housing-площадки; снят через `lg:!max-w-none`.

## 9. Deck / Discard / Resonance — детальная спецификация недостающих ассетов

Референс (`kod-raido-controls-reference.png.png`) содержит 4 блока. Владелец подтвердил их
канонические роли, закрывая ранее открытый вопрос:

- **Блок A** — Deck (колода): рубашка с руной `R`, красная/синяя сторона, счётчики 0/1/25+.
- **Блок B** — Discard (сброс): рубашка с черепом, счётчики 7/12.
- **Блок C** — **это состояния круглого механизма End Turn** (тот же язык, что и утверждённый
  `kod-raido-end-turn-master.webp`), **не вариант Resonance** — несмотря на более раннее
  предположение в этом документе, этот блок нигде дальше не описывается как Resonance.
- **Блок D** — единственный утверждённый Resonance: длинная горизонтальная золотая панель,
  тёмный металлический корпус с золотыми шипованными краями, пять круглых гнёзд,
  последовательное заполнение самоцветами (красный, янтарный, фиолетовый, голубой, синий),
  состояния `0/5`, `3/5`, `5/5`, числовой счётчик справа.

динамических данных). Placement/canvas-размеры привязаны к уже существующим housing-слотам
компонента (`MatchBoard.module.css`, desktop `@media (min-width:1024px)`, сцена 1672×941) — сами
